# Live standalone WAF load test: 2026-10-06

The compiled Carnical executable processed **500,000 measured HTTP requests** through CRS, blocking format inspection and
the reverse proxy. The test used a counted loopback origin, not a mock inspector. It completed in 94.655 seconds, with
5,282.34 requests/second and no transport errors or availability failures. Results still show detection gaps and refusals
of legitimate traffic; the request count is not a claim of complete protection.

[Machine-readable evidence](loadtest-2026-10-06.json) contains every case's response counts and origin admissions, aggregate
latencies, hashes of the executable/corpus files, runtime details, active WAF arguments and observed rule-log counts.
[The harness](../tools/loadtest/main.go) reconstructs the workload and launches the actual executable.

## Configuration and request fidelity

Windows, Go 1.26.6, 12 logical CPUs. The measured interval was 2026-10-05 14:43:38–14:45:12 UTC, or 2026-10-06 in Sydney.
The binary embeds revision `32061afd` with `vcs.modified=true` because the local integration sources were then untracked;
its standalone source was at that revision. Its SHA-256 is
`f880ae3b6ff1c223d9f6b04348175fa76f73cbc73c1f42f04fb87e3a82bb82d3`.
Later publication commits add integration APIs and this harness, without changing the standalone request pipeline used here.

CRS 4.30.0 ran at its default paranoia level 1 and inbound anomaly threshold 5. Both CRS and the format inspector were in
block mode. Response inspection was enabled. API quotas were disabled, so repeated requests were evaluated without a quota
turning every later request away. WordPress-specific protection was not enabled. The origin was a local HTTP server
returning fixed JSON and counting admissions by case; it never executed the submitted payloads.

The workload cycles through 468 benign corpus cases, 247 attack corpus cases and 16 additional regressions: **731 distinct
request templates**, each repeated 683 or 684 times. The 500,000 requests are not 500,000 unique payloads. The clients use
HTTP/1.1, mostly persistent connections, with a fresh body per request and no redirect following. This is a local closed-loop
measurement of the entire executable/proxy path, not a maximum-capacity measurement or a distributed production benchmark.

Corpus hosts are preserved as HTTP Host values; network connections go only to the harness's loopback WAF and origin.
Multipart uploads are rebuilt from corpus file fields. Existing percent escapes and query delimiters retain their wire
spelling; spaces, non-ASCII bytes and punctuation requiring escaping are encoded. In particular, literal `#` is encoded
instead of truncating a payload as a URL fragment. Request construction verifies that the wire request target is unchanged.
Malformed header values and explicit framing headers use raw loopback connections, preserving their bytes rather than
letting Go's HTTP client reject or normalize them. Incomplete framing closes the write side to supply EOF while reading the
server's response. Case `protocol/236` receives 400 in all 684 attempts, with zero origin admissions.

Earlier exploratory runs exposed URL-fragment truncation and framing normalization in the harness. They were corrected
before this final run; their measurements are superseded. The final run was separate from the CPU-heavy package race tests.

monitoring when individual layers are disabled.

## Remaining gaps and false positives

Thirty-four labelled attack templates reached the origin. They include remote-resource URLs, compact shell/Windows command
strings, serialized Java markers, noncanonical loopback and `dict` URLs, two template syntaxes, scanner user agents,
application/plugin paths and fifteen generic probe paths. Those types and their exact corpus indexes remain visible in the
JSON evidence. WordPress virtual patches, an OpenAPI model and the API guard were not installed in this standalone run.
Application-specific rules and guarded application URL fetches are still needed where those inputs would be dangerous.

`protocol/239` embeds an extra header line in a forwarding-host claim. Its valid request reaches the origin; the proxy's
separate identity-header tests cover removal of untrusted forwarding claims. Counting it as admitted does not establish
that the origin trusted the claim. More generally, a successful response from the fixed JSON origin demonstrates admission,
not successful exploitation. Status refusal includes protocol and format rejection as well as CRS detection. 5xx responses
other than the explicit unsupported-method 501 are counted as availability failures, never as attack detection.

Eleven benign templates are refused, each 684 times:

- `search/79`, `/85`, `/99`, `/110`, `/115`, `/164`: ordinary search text colliding with attack signatures.
- `forms/226`: WordPress editor HTML.
- `api/231`: a valid GraphQL Products query. An isolated live replay identifies CRS rule 942290 (MongoDB operator matching)
  and anomaly refusal 949110; the GraphQL variable names collide with that signature. This is a concrete endpoint-tuning case.
- `api/242`: CSP-report media type, refused with 415.
- `api/243`: a plain-text API body, refused with 403.
- `api/245`: an XML-RPC body, refused with 400.

These are reported according to the corpus labels, including policy restrictions. A deployment must validate endpoint
contracts and narrow exclusions against its actual traffic before accepting these false positives or changing the policy.
No protection was weakened to raise the benchmark's detection/admission scores.

## Reproduce

From the repository root, supply the owner's separately maintained corpus directory:

```text
go build -o build/carnical.exe ./carnical/cmd/carnical
go run ./carnical/tools/loadtest -binary D:/Dev/coraza/build/carnical.exe -corpus D:/Dev/5Weeks1k/newsletter/content/waf/corpus -output D:/Dev/coraza/build/loadtest.json -count 500000 -concurrency 16
```

Adjust absolute paths for the host. A rebuild at a later commit will carry different VCS metadata and can have a different
binary hash; every run records its own hash. The input directory needs `benign.jsonl` and `attack.jsonl`; their hashes are in the
evidence. The harness starts its own local origin and WAF, waits for readiness, runs the measured requests, writes the JSON
report and stops its child processes. `-rps` optionally limits the offered rate; this run used the default unpaced setting.

Detailed WAF logs are written alongside the local report and are not committed. Published log-rule counts are a snapshot,
include readiness events and can contain multiple events per request. A forced child shutdown does not claim a final flushed
monitoring snapshot. Production API guard/control/virtual-patch integration, TLS edge termination, Linux confinement,
distributed abuse and long-duration saturation require their own deployment validation.
